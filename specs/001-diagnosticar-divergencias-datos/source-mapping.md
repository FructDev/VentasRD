# Mapeo de fuentes reales para el diagnóstico local (T001)

Este documento caracteriza el código actual, no el esquema instalado en cada cliente. La captura diagnóstica lee solamente IndexedDB y nunca convierte una proyección en autoridad remota.

| Entidad | Tabla Dexie / índices útiles | Hechos locales y límite |
|---|---|---|
| Venta | `ventas`: `id`, `negocio_id`, `fecha_creacion`, `[negocio_id+fecha_creacion]`, `estado_sincronizacion` | `src/app/page.tsx` es el cobro activo. Guarda `id`, `negocio_id`, `sucursal_id?`, `caja_codigo?`, `total`, método/mixto, `cliente_id?`, `ncf?`, `fecha_creacion`, flag. Prueba confirmación **local**, no recepción remota. |
| Líneas | `venta_detalles`: `id`, `venta_id`, `producto_id`, `negocio_id`, `fecha_creacion` | Guarda cantidad, precio y subtotal; no tasa ITBIS ni descuento histórico por línea. Las versiones anteriores a Dexie v10 pueden tener detalles sin `negocio_id`; relacionar por venta y declarar cobertura parcial si no se puede probar alcance. |
| Producto | `productos`: `id`, `negocio_id`, `fecha_actualizacion`, flag | `stock_actual` es proyección local sin sucursal en la fila; `tasa_itbis` es actual, no histórica. `estado_sincronizacion=0` señala edición local pendiente, pero no conserva versión previa. |
| Movimiento | `movimientos_stock`: `id`, `negocio_id`, `producto_id`, `tipo`, `fecha_creacion`, flag | `delta`, `valor_absoluto?`, `referencia_id?`, `sucursal_id?`; el movimiento local se escribe con stock en `src/lib/db/stock.ts`. No hay device ID ni resultado RPC persistido. Un flag 1 no demuestra aplicación remota: el worker puede marcar 1 tras error SQL permanente. |
| Fiado | `transacciones_fiado`: `id`, `negocio_id`, `cliente_id`, tipo, fecha | Cargo de venta con `venta_id` y monto; el cobro activo lo incluye en la transacción principal si es fiado. |
| Serial | `seriales`: `id`, `negocio_id`, `producto_id`, flag | `venta_id?` y estado vendido. El cobro activo actualiza seriales **después** de la transacción de venta, por lo que puede existir una venta confirmada con serial no actualizado. No exponer `numero_serial`/IMEI completo. |
| Devolución | `devoluciones`: `id`, `negocio_id`, `venta_id`, fecha, flag | `items_devueltos` y `monto_devuelto`; no registra método monetario de reembolso. |
| Caja/corte/gasto | `cajas`, `cortes_caja`, `gastos`: índices `negocio_id`; cortes con `caja_id`, gastos con `[negocio_id+fecha_creacion]` | `CajaModal.tsx` consulta ventas por fecha de apertura sin filtro de negocio/sucursal/caja en esa consulta. `VentaLocal.caja_codigo` no referencia `CajaLocal.id`; con ventanas superpuestas no existe atribución causal segura. Gastos y pagos Pro filtran negocio y fecha, pero tampoco `caja_id` ni sucursal. El esperado sí incluye la porción en efectivo de mixto, mientras `CorteCajaLocal.efectivo` conserva solo ventas clasificadas como efectivo más Pro. |
| Pro | `reparaciones`, `apartados`: `negocio_id`, `sucursal_id`, fecha | Pagos/abonos anidados; contienen contacto, IMEI y PIN/patrón que deben excluirse. Reparaciones antiguas pueden carecer de historial `pagos`; `CajaModal` reconstruye abono/saldo y usa efectivo si falta método. Esa reconstrucción se etiqueta como legado/no comparable, no como historial completo. No extrapolar pagos al POS. |
| Reportes | Sin tabla local específica; `src/lib/exports/queries.ts` calcula al solicitar | Ventas brutas, ITBIS derivado de `producto.tasa_itbis` **actual**; un valor histórico puede ser irreproducible. No inventar `ObservedReportValue` en US1. |

El worker purga ventas y detalles sincronizados de más de 90 días, movimientos de más de 30 días, y devoluciones/cortes de más de 90 días (`src/lib/db/worker.ts`). La captura de un período anterior debe declarar retención parcial, no “cero filas”. Los índices por negocio/fecha se incorporaron en diferentes versiones Dexie (v7–v21); el lector de este checkpoint requiere una base ya abierta con las tablas v21 y falla sin emitir informe si alguna falta. Abrir/actualizar una base antigua es responsabilidad del flujo existente, no de este diagnóstico. La venta actual crea venta, detalles, fiado y movimiento en transacción `rw`, pero la actualización de serial está fuera; no usar el contrato experimental `confirmarVentaLocal.ts` como prueba del cobro activo.

La identidad offline proviene del contexto local ya desbloqueado. El lector acepta el `negocioId` solicitado sin certificar permiso server-side; no se habilita exportación ni comparación con otro negocio por ello. No hay base histórica de stock garantizada por estas tablas: `valor_absoluto` solo sirve como ancla si hay orden causal y cobertura desde entonces.
